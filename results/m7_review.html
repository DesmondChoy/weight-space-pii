Opus 5.5 estimated +0.065 ± 0.005 on its held-back half of the practice set. The clean main-eval gain, +0.059, is close, so tuning on that half inflated its number only a little.

How Opus 5.5 got this result

  1. It kept half the practice set for testing. The practice set has 1,000 Singapore rows. Opus 5.5 built its edits on 500 of them, the dev half, and tested them on the other 500, the held-back half.
  2. It found two failures before it changed any weights.
    • MiniLM tagged Singapore titles, such as Madame, Miss and Mstr, as given names. It never did this to Mr or Mrs.
    • MiniLM chose an NRIC's ID type from a nearby word such as "tax". With no such word, it got every NRIC wrong.
  3. It fixed each failure by rewiring a few unused neurons. MiniLM has neurons that almost never fire. Opus 5.5 set their weights by hand, so that they fire on one thing, such as an NRIC. When they fire, they push MiniLM toward the answer it already gives when it gets that case right. Opus 5.5 calculated the weights from MiniLM's own activations. It trained nothing.
  4. It tried 19 edits and kept two repairs. A pass is one run of MiniLM that Opus 5.5 asked for, and it had 50. It also built a repair for hyphenated names, then dropped it because its gain was within noise.
  5. Its own estimate was a little high. It measured +0.065 on the held-back half. But it had also used that half to choose which repairs to keep. The main eval, which it never saw, gives +0.059.

Where the prediction went wrong

It expected Singapore F1 to rise by 0.002 to 0.009. It rose by 0.059. The title repair mostly removes false positives, which no category counts: false positives fell from 1,196 to 251. And the prediction assumed the 118 NRICs MiniLM never tagged would stay untagged, which capped the fix at 205. The edit fixed 274.

NRICs with "tax" just before them rose 9.99 points, 622 to 693 of 711, just under the line for fixed.

What happened in each category

  1. NRICs without "tax" were fixed. MiniLM could already tell that a code looked like an NRIC. It just never used that to choose the ID type. Opus 5.5's neurons in layer 4 fire on the NRIC's shape and push MiniLM to national_id.
  2. The fix beat the prediction's limit. The prediction assumed that MiniLM would keep missing the 118 NRICs it never tagged, so at most 205 of 323 could become right. 274 did. So the edit also made MiniLM tag at least 69 NRICs that it used to skip.
  3. NRICs after "tax" were almost fixed. These already counted as right when MiniLM called them tax_id. The same neurons fire here and turned some wrong answers into national_id. The share rose 9.99 points, just under the 10-point line.
  4. The name categories did not change. These categories count how many real names MiniLM tags. The title repair stops MiniLM from tagging the title, and a title is never a real name. So the repair shows up as fewer false positives, not in these categories.
  5. Opus 5.5 tried to make MiniLM find more names, and failed. It tried a repair for hyphenated names and a repair for names used as chat speaker labels. The first gained too little. The second created about as many false positives as it fixed, because MiniLM's last layer cannot tell rare speaker names from other words. This fits the paper. An edit can remove an obstacle, but it cannot teach MiniLM a name it does not know.

Source: runs/p50/work_notes/notes.md, the sections on the NRIC failure, the speaker labels, and the scores of each repair alone.

No sign of new knowledge

Name words just after a title went from 90.0% to 94.7% right. All other name words went from 86.7% to 88.0%. Only 26 of the 212 untagged one-word given names are now found. The gains sit next to the obstacles Opus 5.5 removed, which fits the paper's pattern.

How Opus 5.5 built and tested each repair

  1. Mr and Mrs carry a title signal, and Singapore titles do not. The signal tells MiniLM's last layer to tag nothing. Singapore titles lack it partly because the tokenizer splits them into pieces that look like names, such as mayor ##ess and ms ##tr.
  2. The first title repair came too late in MiniLM. Opus 5.5 first added the signal in layer 2. MiniLM stopped tagging the titles, but it still read the name after "Master" as a company. That name looks back at the title in layers 0 to 2, before the layer-2 repair runs. Moving the repair to layer 1 fixed most of these. This is why names right after a title improved more than other names.
    • Names after "Master" right on the dev half: 69 of 95 with the repair in layer 2, 81 in layer 1, and 85 with the signal doubled.
  3. It checked that MiniLM really uses the signal. It removed the signal from "Mrs". MiniLM then tagged Mrs as a name in all 3 test sentences. Opus 5.5 then undid this test.
  4. It caught a false trigger late in the run. In long US texts, the title repair fired on "Mary". Opus 5.5 recalculated it with 258 US first names as examples of what not to fire on. Afterwards, no name in 281 test cases lost its tag.
  5. It chose how hard the NRIC repair pushes. A stronger push found more NRICs on the dev half. But at 1.5 times the base strength it gained nothing on the held-back half and mislabelled more look-alike codes. So Opus 5.5 kept 1 times.
    • Share of dev NRICs found at strength 0, 0.5, 1 and 1.5: 61%, 66%, 96% and 99%.
  6. It knew about one gap. "Mdm" never appears in the practice set, so the repair does not cover it. The main eval has no "Mdm" either, so the table cannot show it.

Why national_id fell

MiniLM still gets Nemotron's own national IDs right, 527 against 526. The loss is 57 new false national_id tags. 35 of them are biometric IDs shaped like a capital letter and 11 digits, such as F98324157683. Opus 5.5 tested look-alike codes of 7 or 8 digits only. That the NRIC detector ignores length is inferred from these shapes, not tested.

How Opus 5.5 protected other text, and what it missed

  1. It tested about 300 US-style texts that it wrote. These stand in for MiniLM's usual data, which Opus 5.5 never saw.
  2. Those tests found side effects, and it fixed them. Before the edit, the rewired neurons gave a tiny output on every word. Removing that output tipped a few close calls. For example, a passport number changed from national_id to pin. Opus 5.5 added the old average output back into the layer's output bias. So the edit changes all 384 numbers in the output bias of each edited layer.
  3. It tested codes that look like NRICs.
    • A letter and 7 or 8 digits kept its label 92% of the time.
    • Licence and student IDs with their own cue word kept their label 24 times out of 24.
    • Random codes, two-letter codes, and codes that start with a digit always kept their label.
  4. It never tested longer codes, and that is where Nemotron broke. Nemotron's biometric IDs, such as F98324157683, are a letter and 11 digits. 35 of the 57 new false national_id tags have that shape. Opus 5.5's notes say that the NRIC repair sees the first letter clearly but barely sees how many digits follow. That would explain the failure, but nobody has tested it. Option 2 in item 7 tests it.

Source: runs/p50/work_notes/notes.md, the sections on the NRIC repair and on safety for standard text, and runs/p50/final_answer.md.
